# 06 · 联调排错手册

> 读完你能做什么：独立判断一个接口问题是「路由错」「参数错」「后端异常」还是「真跨域」，并用最少步骤定位到具体文件；能背出本项目踩过的 10 类坑的解法。

---

## 1. 联调前的 6 项检查

按顺序过一遍，能排除一半的问题：

| # | 检查项 | 怎么查 | 期望结果 |
| --- | --- | --- | --- |
| 1 | 后端是否在跑 | 浏览器打开 `http://localhost:5000/ping`，或任务管理器看 5000 端口 | 有响应（本项目 `/ping` 会抛异常，见下方说明） |
| 2 | 前端是否在跑 | 打开 `http://localhost:5173` | 页面正常渲染 |
| 3 | 端口是否对得上 | `src/config/index.ts` 的 `BASE_URL` | 与后端实际端口一致（本项目 5000） |
| 4 | 路由是否对得上 | `internal/router/router.py` | 前端请求的 path 与后端注册的 path 完全一致 |
| 5 | 参数格式是否对得上 | 两者 model 定义 | 例如 `app_id` 必须是合法 UUID |
| 6 | 环境变量是否齐 | `.env` 与 `os.getenv` | 尤其 `OPENAI_API_KEY`、`OPENAI_API_BASE` |

> 本项目 `/ping` 被改成了 `raise FailException("数据未找到")`，所以它返回 500 是**故意的**，不能拿它判断服务是否存活。更可靠的方式是直接调 `/apps/<真实uuid>/debug`。

---

## 2. 打开 Network 面板，先看三样东西

按 F12 → Network → 复现一次操作，然后看：

1. **状态码**：`200` 正常；`404` 路径或 UUID 格式不对；`400` 参数校验失败；`500` 后端异常；`0` 或被标红且无状态码 → 通常是网络/跨域。
2. **响应头里有没有 `Access-Control-Allow-Origin`**：这是判断“真/假跨域”的唯一标准。
3. **Response 内容**：如果返回的是 Werkzeug 的 HTML 调试页，说明异常没被你的异常处理器接住，跨域头也不会加。

一个小技巧：`OPTIONS` 请求是浏览器的预检（preflight），当你发送 `Content-Type: application/json` 或自定义头时才会出现。预检失败，真正的 POST 根本不会发出。

---

## 3. 跨域问题分四种情形

| 情形 | 现象 | 根因 | 处理 |
| --- | --- | --- | --- |
| A. 真跨域 | `OPTIONS` 返回 200 但没有 `Access-Control-Allow-Origin` | 后端没配 CORS，或 `origins` 不含前端地址 | 配置 `CORS(...)` 或改用 Vite 代理 |
| B. 预检被拦 | `OPTIONS` 返回 403/405 | `methods`/`allow_headers` 没覆盖实际请求 | 放开方法或请求头 |
| C. 假跨域（本项目踩过） | POST 返回 404 或 500，且**没有** CORS 头 | 错误响应绕过了 CORS 中间件 | 先修业务错误，再让异常也返回 JSON |
| D. 前端地址变了 | 换了端口（5174、5175）后突然跨域 | 后端只允许 5173 | 加白名单或用代理 |

判断顺序永远是：**先看状态码，再看响应头**。状态码不是 200 时，优先当成业务错误处理，不要一上来就怀疑 CORS。

---

## 4. 假跨域完整复盘（重点案例）

### 4.1 现象

前端请求 `POST http://localhost:5000/apps/1/debug`，浏览器控制台报：

```
Access to fetch at 'http://localhost:5000/apps/1/debug' from origin 'http://localhost:5173'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present...
```

### 4.2 定位过程

```powershell
# 用 curl.exe 直接打后端，绕开浏览器
curl.exe -i -X POST "http://localhost:5000/apps/1/debug" `
  -H "Content-Type: application/json" -H "Origin: http://localhost:5173" `
  -d '{\"query\":\"你好\"}'
```

响应：

```
HTTP/1.1 500 INTERNAL SERVER ERROR
Content-Type: text/html; charset=utf-8
（没有任何 Access-Control-Allow-Origin）
```

看到 500 且响应是 HTML，就说明问题不在 CORS 配置。

### 4.3 根因链条

```
1. 路由是 /apps/<uuid:app_id>/debug，uuid 转换器要求合法 UUID
2. 传的是 1 → 转换失败 → 抛 404
3. 全局异常处理器在 debug 模式下执行 raise error（见 internal/server/http.py）
4. 异常脱离 Flask 响应链，交给 Werkzeug 调试中间件渲染 HTML
5. flask-cors 的 after_request 没有机会执行 → 响应缺少 CORS 头
6. 浏览器只能报“跨域”，真实错误被掩盖
```

### 4.4 正确做法

1. 用数据库里的真实 UUID 请求，例如：
   `POST http://localhost:5000/apps/f670e322-39a2-4e5a-9a7a-9d3732c451bf/debug`
   实测返回 `200`，且带 `Access-Control-Allow-Origin: http://localhost:5173`。
2. 长期修复：把异常处理器里的 `raise error` 改为返回 JSON（同时把堆栈写日志），让所有错误都走 Flask 响应链、都能带上 CORS 头。

```python
if self.debug or os.getenv("FLASK_ENV") == "development":
    self.logger.exception(error)          # 堆栈进日志/控制台
    return json(Response(code=HttpCode.FAIL, message=str(error), data={})), 500
```

> 结论：跨域报错只是“症状”，先确认状态码。404/500 的响应通常不带 CORS 头，这是浏览器规则，不是后端配置错了。

## 5. 真跨域的两个解法

### 5.1 方案一：后端配置 CORS（本项目采用）

```python
from flask_cors import CORS

CORS(
    self.app,
    resources={r"/*": {"origins": "*"}},   # 生产环境请写具体域名
    supports_credentials=True,
)
```

要点：

- 不要无谓地限制 `methods` 和 `allow_headers`。本项目曾限定为 `["GET", "POST"]` 和 `["Content-Type"]`，以后一旦用 `PUT`/`DELETE` 或自定义头就会被预检拦住。
- `supports_credentials=True` 时，`origins` 不能是 `*`，必须写具体地址（浏览器的安全限制）。

### 5.2 方案二：Vite 代理（彻底同源，推荐生产思维）

```ts
// vite.config.ts
export default defineConfig({
  plugins: [vue(), tailwindcss()],
  resolve: { alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) } },
  server: {
    port: 5173,
    proxy: {
      '/api': {
        target: 'http://localhost:5000',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  },
})
```

配套把 `src/config/index.ts` 的 `BASE_URL` 改为 `'/api'`。这样浏览器只请求 `http://localhost:5173/api/...`，同源，不存在任何 CORS；由 Vite 开发服务器转发到 5000。

## 6. 不用浏览器，直接验证后端

```powershell
# 1. 预检是否正常
curl.exe -i -X OPTIONS "http://localhost:5000/apps/f670e322-39a2-4e5a-9a7a-9d3732c451bf/debug" `
  -H "Origin: http://localhost:5173" `
  -H "Access-Control-Request-Method: POST" `
  -H "Access-Control-Request-Headers: content-type"

# 2. 正式请求
curl.exe -i -X POST "http://localhost:5000/apps/f670e322-39a2-4e5a-9a7a-9d3732c451bf/debug" `
  -H "Content-Type: application/json" -H "Origin: http://localhost:5173" `
  -d '{\"query\":\"你好\"}'
```

看三处即可：状态码、`Access-Control-Allow-Origin`、响应体里的 `code`。

## 7. 报错速查表

### 7.1 安装与工程化

| 报错 | 根因 | 解决 |
| --- | --- | --- |
| `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` | pnpm 12 供应链策略拒绝“发布太新”的包 | 重建锁文件（`pnpm clean --lockfile` + `pnpm install`），或在 `pnpm-workspace.yaml` 的 `minimumReleaseAgeExclude` 豁免 |
| `ERR_PNPM_UNEXPECTED_STORE` | `node_modules` 由另一个 store 链接而来 | 在正常终端 `pnpm install` 重新链接；必要时 `pnpm install --force`；不要手删 `node_modules` |
| `'vite' 不是内部或外部命令` | 依赖没装上，`node_modules/.bin` 为空 | 先解决上面的安装错误，再 `pnpm dev` |
| 提交被 `no-empty-source` 拦 | 空的 `<style scoped></style>` | Stylelint 配置 `'no-empty-source': null` |
| 提交被 `no-explicit-any` 拦 | 显式写了 `any` | 视团队规范决定；本项目设为 `off`，注意它不影响隐式 any |
| 提交被 commitlint 拦 | 提交信息格式不对 | 用 `feat: xxx`、`fix(scope): xxx` 等 Conventional Commits 格式 |

### 7.2 样式

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| `h-16`、`px-4` 全部不生效 | 引入了 Tailwind v3 的入口（`@tailwind base`），v4 不认 | 改引 `src/style.css`，内部是 `@import "tailwindcss"` |
| 自定义类 `scrollbar-w-none` 无效 | v4 需要用 `@utility` 定义 | 在 `style.css` 中 `@utility scrollbar-w-none { scrollbar-width: none }` |
| `text-brand` 无效 | 主题色没定义 | 在 `@theme` 中定义 `--color-brand` |
| Arco 组件样式错乱 | 没引入 `arco.css`，或引入顺序不对 | 先 `arco.css` 再 `style.css` |

### 7.3 前端运行时

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| `<a-button>` 不渲染、无报错 | 没 `app.use(ArcoVue)` | 在 `main.ts` 注册 |
| `<icon-send>` 不显示 | 没 `app.use(ArcoVueIcon)` | 注册图标库，或按需 import |
| 访问 `/space/apps/xxx` 白屏 | 路由没配或 Layout 里漏了 `<router-view />` | 检查 `router/index.ts` 与 Layout |
| 聊天页消息多了看不到最新 | 没有滚动到底逻辑 | `nextTick` 后 `container.scrollTo` |
| `v-for` 警告重复 key | `:key="message.content"` 内容重复 | 改用自增 id |

### 7.4 后端与 LangChain

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| 404 on `/apps/<id>/debug` | id 不是合法 UUID | 用数据库真实 UUID |
| `Missing credentials` | 没有 `OPENAI_API_KEY` | 写入 `.env`，确保 `dotenv` 在 `ChatOpenAI` 实例化前执行 |
| 请求发到了 `api.openai.com` | `.env` 里写的是新变量名或没加载 | 使用 `OPENAI_API_BASE`，并在构造模型前 `load_dotenv()` |
| `KeyError: 'query'` | 模板变量与 `invoke` 字典键不一致 | 两者保持同名 |
| 500 且响应是 Werkzeug HTML | 异常被重新抛出，绕过响应链 | 改为返回 JSON；同时这也会伪装成跨域 |
| 任意 UUID 都能聊天 | `debug` 未使用 `app_id` | 属当前章节行为，后续用 `app_id` 查库即可 |

## 8. LangChain 环境变量排错

`ChatOpenAI(model=...)` 不传 key 时，按以下顺序解析：

```
base_url: 显式参数 → OPENAI_API_BASE → OPENAI_BASE_URL → https://api.openai.com/v1
api_key : 显式参数 → OPENAI_API_KEY
```

排查步骤：

1. 打印 `os.getenv("OPENAI_API_BASE")`、`bool(os.getenv("OPENAI_API_KEY"))`。
2. 确认 `dotenv.load_dotenv()` 执行在 `ChatOpenAI(...)` 之前。
3. 如果打印为空但服务能跑，说明是**启动它的那个终端/PyCharm 运行配置**里临时注入了变量，`.env` 本身并不完整——换终端就会失败。把 key 补进 `.env` 才是可复现的做法。

---

## 9. 排查方法论（记住这五条）

1. **先分层，再动手**：浏览器 → 前端代码 → 网络 → 后端路由 → 业务 → 模型。一次只验证一层。
2. **用 curl 绕开浏览器**：能区分“前端问题”和“后端问题”，还能看到真实状态码与响应头。
3. **跨域先看状态码**：非 200 的响应本来就不该有 CORS 头，别被浏览器的措辞带偏。
4. **一次只改一个变量**：同时改端口、路由、参数，成功了也不知道是哪一步生效的。
5. **把结论写下来**：报错原文 + 根因 + 解法，三条一起记，下次命中率极高。
