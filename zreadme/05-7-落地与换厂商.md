## 一、对齐项目代码：逐行拆 `debug()`

```python
prompt = ChatPromptTemplate.from_template("{query}")
llm = ChatOpenAI(model="deepseek-flash")
parser = StrOutputParser()
chain = prompt | llm | parser
content = chain.invoke({"query": req.query.data})
return success_json({"content": content})
```

| 代码 | 说明 |
| --- | --- |
| `ChatPromptTemplate.from_template("{query}")` | 只有 `HumanMessage` 占位的最简模板 |
| `ChatOpenAI(model="deepseek-flash")` | 只换 model；base_url/key 从 `.env` 读 |
| `StrOutputParser()` | `AIMessage` → `str` |
| `chain = prompt \| llm \| parser` | 三步用 `\|` 串成一条链 |
| `chain.invoke({"query": req.query.data})` | 校验后的用户输入 |

**唯一实质差别是模型名**（学习示例常用 `gpt-3.5-turbo-16k`，项目用 `deepseek-flash`，其余只多了一层 `success_json` 包装）。DeepSeek 提供 OpenAI 兼容接口，`ChatOpenAI` 把 `base_url` 指过去、换成对方模型名即可，**上层链一行不改**——这就是抽象的价值。

补充两点：`debug(app_id)` 里的 `app_id` **未参与业务**，只用路由层 uuid 校验，后续章节才会 `app_service.get_app(app_id)`；`print('生成内容:', content)` 是临时调试，正式环境换结构化日志。

## 二、不用 LangChain 时：同一个接口要写这么长

同样是 `debug()`，手写 openai SDK 的最小等价实现：

```python
import os

from openai import OpenAI

from internal.schema.app_schema import CompletionReq
from pkg.response import success_json, validate_error_json

client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_API_BASE"),
)


@user_required
def debug(self, app_id: UUID):
    req = CompletionReq()
    if not req.validate():
        return validate_error_json(req.errors)

    # 原来 prompt | llm | parser 三步，展开成这样
    messages = [{"role": "user", "content": req.query.data}]
    resp = client.chat.completions.create(model="deepseek-flash", messages=messages)
    content = resp.choices[0].message.content or ""

    return success_json({"content": content})
```

差别不在行数（这一版甚至更短），而在于**能力边界**：

| 后续需求 | LangChain | 手写 openai SDK |
| --- | --- | --- |
| 加 system 人设 | 模板里加一行 `("system", ...)` | 手动在 `messages` 头部插 dict |
| 加历史 | `MessagesPlaceholder` + 传 `chat_history` | 自己维护并 `append` 历史列表 |
| 换模型/换厂商 | 换一行构造代码 | 换 SDK、参数名、结果解析 |
| 加流式接口 | `chain.stream(...)` | 新写一套 `stream=True` 循环 + SSE |
| 加批量调试 | `chain.batch([...])` | 自己开线程池 |
| 加日志/耗时 | 传 `config={"callbacks": [...]}` | 每处调用都包 try/finally |

## 三、扩展阅读：换厂商只换模型类

换厂商的最小示意只有两行：

```python
from langchain_community.chat_models.baidu_qianfan_endpoint import QianfanChatEndpoint
chat_model = QianfanChatEndpoint()
```

它想表达：只要都实现 `Runnable` 接口，`ChatOpenAI` / `QianfanChatEndpoint` / `ChatOllama` 之间可以互换，`chain = prompt | llm | parser` 之后完全一样。**换模型 = 换一行构造代码**，这也是项目要把「模型构建」与「链编排」分开写的原因。注意：`QianfanChatEndpoint` 需装 `langchain-community` 并配 `QIANFAN_AK`/`QIANFAN_SK`；各厂商对 system 消息、流式格式支持不完全一致，个别场景仍需适配。

对照手写版：

| 场景 | LangChain | 手写 |
| --- | --- | --- |
| OpenAI 兼容厂商（DeepSeek / Qwen / Moonshot） | `ChatOpenAI(model=..., base_url=...)` 即可 | 换 `model` 与 `base_url` 两个参数即可，**不用改代码结构** |
| 非 OpenAI 兼容厂商（千帆、Ollama 原生协议） | 换模型类，链不动 | 换 SDK、重新学结果结构，调用代码要重写一遍 |
| 流式格式差异 | 模型类内部适配成 `AIMessageChunk` | 各家 `delta` 结构不同，逐个适配 |

所以“换厂商只换模型类”这句话的前提是：**模型类负责把厂商差异收敛成统一协议**。手写版没有这层收敛，兼容接口能靠 `base_url` 蒙混过关，不兼容的就得改业务代码。
